# 器材资产、排序与分类筛选开发计划

- 状态：待开发
- 制定日期：2026-07-22
- 适用范围：器材列表、器材表单、器材查询 API、资产统计 API
- 文档生命周期：本计划仅在开发和验收期间保留。全部验收完成后，将长期有效的合同同步到 `docs/api.md`、`docs/database.md` 和必要的 README，再删除本文件，避免 `docs/` 留存失效计划。

## 1. 目标

本轮开发解决三个问题：

1. 胶片的资产价值按单卷估值乘库存数量计算。
2. 器材列表按相机、镜头、配件、胶片分组排序，每组按购买日期从新到旧排列。
3. 选择镜头类型时显示镜头卡口筛选；选择相机类型时显示相机分类筛选，分类为微单、胶片、拍立得、CCD。

完成后的核心体验是：用户打开器材页即可按固定类别顺序浏览；切换器材类型后只看到与该类型有关的二级筛选；统计页和仪表盘展示的资产总额能够正确反映胶片库存数量。

## 2. 现状结论

- `items.current_value` 已作为资产统计口径；新增器材只填写 `purchase_price` 时，后端会把它作为初始 `current_value`。
- `films.quantity` 已存在并用于胶片库存统计。
- `lenses.mount` 和 `cameras.mount` 已存在，`GET /api/items` 也已有通用 `mount` 参数。
- `cameras.camera_type` 已存在，但当前表单允许任意文本，列表 API 尚不能按该字段筛选。
- 器材页当前固定请求 `sort=-created_at`，因此按录入时间而非购买时间排序。
- 统计摘要、品牌统计和类型统计当前都把每条胶片的 `current_value` 只计算一次。

结论：本轮不需要新增字段或执行数据库迁移。重点是统一统计算法、增加查询能力，并把现有字段收敛为可用的交互选项。

## 3. 已确定的业务规则

### 3.1 资产价值

单条器材的资产贡献定义为：

$$
V_i =
\begin{cases}
0, & \text{status} \ne \text{owned} \\
q_i \times v_i, & \text{type} = \text{film} \\
v_i, & \text{其他持有器材}
\end{cases}
$$

其中：

- $v_i$ 为 `current_value`；空值按 $0$ 处理。
- $q_i$ 为关联 `Film.quantity`；空值按 $0$ 处理。
- `purchase_price` 不直接参与统计，它仍只负责记录购买价格，并在创建时作为 `current_value` 的默认来源。
- 胶片的 `current_value` 和 `purchase_price` 均解释为单卷价格。界面字段需要明确标注该语义。
- 继续沿用当前项目的币种前提：统计直接汇总数值，不在本轮增加汇率换算。

以下接口必须共用同一个资产计算函数，避免总额与分组小计不一致：

- `GET /api/stats/summary`
- `GET /api/stats/by-brand`
- `GET /api/stats/by-type`

### 3.2 器材排序

列表使用新的显式排序模式 `catalog`，顺序为：

1. 相机 `camera`
2. 镜头 `lens`
3. 配件 `accessory`
4. 胶片 `film`
5. 未知旧类型放在最后，仅作为兼容兜底

每一类内部依次按以下字段排序：

1. 有购买日期的记录在前，`purchase_date` 从新到旧；
2. 未填写购买日期的记录在该类型末尾；
3. 日期相同时按 `created_at` 从新到旧；
4. 仍相同时按 `id` 从大到小，保证分页稳定。

`GET /api/items` 现有的默认排序继续保持 `-created_at`，避免无意改变其他调用方。器材页显式请求 `sort=catalog`。筛选只移除不匹配的记录，不改变剩余记录的相对顺序，因此筛选前后不会出现无理由跳位。

本轮只调整卡片顺序，不增加类别标题或折叠分区。

### 3.3 镜头卡口筛选

- 仅当一级类型为“镜头”时显示“镜头卡口”筛选栏。
- 请求使用现有组合：`type=lens&mount=<卡口>`，不新增 `lens_mount` 字段或查询参数。
- 卡口选项从未筛选的镜头数据中提取，忽略空值、去重并按中文区域规则排序。
- 切换离开镜头类型时立即清除已选卡口，防止隐藏条件继续影响结果。

### 3.4 相机分类筛选

复用 `cameras.camera_type`，不新增数据库字段。新数据使用稳定英文值，界面显示中文标签：

| 存储值 | 显示值 |
| --- | --- |
| `mirrorless` | 微单 |
| `film` | 胶片 |
| `instant` | 拍立得 |
| `ccd` | CCD |

具体规则：

- `GET /api/items` 新增可选参数 `camera_type`，通过 `Camera.item_id` 子查询筛选。
- 仅当一级类型为“相机”时显示“相机类型”筛选栏。
- 切换离开相机类型时立即清除已选相机分类。
- 器材表单把相机类型自由输入改为选择框，并保留“未设置”。
- 编辑已有非标准值时，选择框额外显示该原值；用户未主动修改时原样提交，不静默覆盖。
- 为兼容常见旧值，查询时只做非破坏性别名匹配，不改写数据库：
  - `mirrorless` 同时匹配 `mirrorless`、`微单`；
  - `film` 同时匹配 `film`、`film_camera`、`胶片`、`胶片机`；
  - `instant` 同时匹配 `instant`、`instant_camera`、`拍立得`；
  - `ccd` 不区分大小写。
- 其他旧自由文本值继续在“全部相机”结果和详情页中正常显示，只是不归入四个标准筛选项。

### 3.5 筛选交互

- 筛选栏顺序为：关键词、器材类型、条件二级筛选、品牌、状态、清除。
- 二级筛选使用渐进式展示，不同时展示镜头卡口和相机类型。
- “清除”按钮同时恢复一级和二级筛选。
- `hasActiveFilters` 必须包含两个二级筛选状态。
- 品牌和镜头卡口选项来自未筛选全集，不能因为当前筛选结果变化而消失。
- 请求只发送当前类型适用的二级参数，前后端都不能依赖隐藏控件状态。

## 5. 测试目录约定

当前仓库没有自动化测试目录。若实施时新增 `backend/tests/`，必须先在 `AGENTS.md` 写入以下约定，再创建测试文件：

- `backend/tests/` 只放后端回归测试，文件命名为 `test_<domain>.py`；
- 优先使用 Python 标准库 `unittest` 和项目现有依赖，不为本轮单独引入测试框架；
- 数据测试必须使用内存数据库或 `/tmp` 中的临时数据库，禁止读写 `data/gear.db`；
- 每个测试自行建表、造数和清理，不依赖用户真实数据或执行顺序。

建议新增：

## 7. 回归测试矩阵

### 7.1 资产统计

| 场景 | 期望资产贡献 |
| --- | ---: |
| 持有相机，`current_value=1000` | 1000 |
| 持有胶片，`current_value=50`、`quantity=3` | 150 |
| 已出售胶片，`current_value=50`、`quantity=3` | 0 |
| 持有胶片，`current_value=null`、`quantity=3` | 0 |
| 持有胶片，`current_value=50`、`quantity=null` | 0 |

### 7.2 排序

- 混合四种类型时严格按相机、镜头、配件、胶片排列。
- 同类型内购买日期较新的记录在前。
- 未填写购买日期的记录位于该类型末尾。
- 相同购买日期使用 `created_at` 和 `id` 得到确定顺序。
- 数据超过一页时，连续取页后没有重复或遗漏。
- 使用原有 `sort=-created_at` 时行为不变。

### 7.3 筛选

- `type=lens&mount=Leica M` 只返回对应卡口镜头，不返回同卡口相机。
- `type=camera&camera_type=mirrorless` 能命中新值 `mirrorless` 和兼容旧值 `微单`。
- `camera_type=ccd` 不区分 `ccd` 与 `CCD`。
- 类型、品牌、状态、关键词和二级筛选可组合使用。
- 从镜头切换到相机后不再发送 `mount`；从相机切换到镜头后不再发送 `camera_type`。
- 旧的未知相机类型仍可在全部相机中查看、打开和原样保存。

## 9. 风险与回滚

- 最大风险是把胶片整盒总价误当成单卷价格。通过表单标注和 API 文档把 `current_value` 固定解释为单卷估值；不自动转换历史金额。
- 相机类型历史值是自由文本，不能可靠地自动归类。仅对明确别名做查询兼容，其他值原样保留，由用户在编辑时主动选择标准分类。
- 排序必须在数据库查询中完成，不能先分页再由前端分组，否则跨页顺序会错误。
- 本轮没有 schema 变更和批量数据转换。若需回滚，只需恢复代码和文档；SQLite、`uploads/`、`data/` 均无需恢复。
